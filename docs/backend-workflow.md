# 백엔드 진행 규칙

Spring Boot와 Supabase PostgreSQL로 개발한다. 구현 기준은 Java 21, Gradle Wrapper다.

[노션 작업 보드](https://app.notion.com/p/3e15b2d1a55f819083b1de4e146a84d2)에서 작업을 하나씩 골라 진행하고, 카드와 PR을 서로 연결한다.

## 브랜치와 병합

`main` → `backend/<작업-ID>-<설명>` → PR → 검증 → squash merge

- 예: `backend/b-03-read-api`, `backend/b-06-chat-storage`
- PR 본문, 병합 코멘트, 노션에도 같은 브랜치 이름을 적는다.
- 새 작업은 최신 `origin/main`에서 시작한다. 한 카드에 한 PR을 대응시킨다.
- PR 제목에 작업 ID를 넣는다. 예: `[B-03] 보호소·강아지 조회 API 추가`
- 작업 중에는 Draft PR을 사용할 수 있다. 확인할 준비가 되면 Draft를 해제하고 노션을 `확인 요청`으로 바꾼다.
- 기능에 맞는 테스트와 필요한 빌드·CI를 통과하고 미해결 리뷰가 없어야 병합한다. 문서만 수정한 경우에는 문서 검토 결과를 적는다.
- 병합 직전에 검증한 HEAD SHA와 PR의 현재 HEAD SHA를 비교한다. 달라졌다면 변경 범위를 다시 검토한다.
- 병합 방법은 squash. PR 하나의 결과가 `main`에 커밋 하나로 남도록 한다.
- 브랜치는 병합 확인 뒤 정리한다. 기존 작업 브랜치나 사용자의 미완료 변경은 건드리지 않는다.

B-01은 기존 API 초안을 기준으로 [저장 구조](data-model.md)를 정의했다. 사용자 요청으로 B-03도 기존 초안을 따라 구현하고 [조회 응답 기준](read-api.md)을 문서화했다. B-04는 Supabase Auth 검증과 서버 DB 소속 검사로 구현했으며 [인증·권한 연결 기준](auth-and-permissions.md)을 따른다. C-02의 로그인 제공자·화면 흐름·사진 공개 조건과 C-03의 프론트 합의 전체가 끝난 것은 아니다. 실제 앱 연결 및 B-08 전에 남은 조건을 합의한다. B-05는 [동물·관찰 관리 API](dog-management-api.md)를 구현하고, 저장 트랜잭션의 권한 잠금과 동시 수정 검사를 적용했다. B-06은 사용자 요청에 따라 B-10보다 먼저 진행했고, [대화 저장 API](chat-storage-api.md)에 본인 소유권·중복 전송·상태 변경 검사를 구현했다. 사용자 요청으로 B-07도 이어서 구현했다. [기록 기반 답변](grounded-chat-api.md)은 V2 선점·재시도와 근거 확인을 사용하며, 실제 키 호출·가상 질문 답변 품질은 Q-02에서 검증했다. 개발 DB V2/V3는 이후 B-10A에서 적용했다. 사용자 요청에 따라 B-08도 B-10보다 먼저 구현했다. [사진 조회 기준](photo-read-api.md)은 본인의 완료된 답변 1회 후 공개와 사용 허가 검사를 적용한다. 횟수 1회는 기존 흐름을 바탕으로 둔 구현 기준이며 C-02 전체 합의는 별도이며 실제 Storage 설정은 이후 B-12에서 확인했다. 사용자 요청으로 B-10의 [8종 행동 설정](dog-behavior-api.md) 저장·확인·앱 조회도 구현했다. [B-10A 실제 DB 적용](supabase-development-db.md)도 완료했다. B-09의 [개인 입양 준비 메모](adoption-notes-api.md)도 구현했다. 기존 V1 테이블로 본인 메모의 저장·교체·단건·목록 조회와 동시 저장 충돌을 처리하며 DB 변경은 없다. B-11에서 [실제 서버↔개발 DB 연결](supabase-server-connection.md)과 HTTP 조회·미인증 차단을 검증했다. 실제 로그인 저장은 B-13에서 검증했다. AI 실제 호출은 Q-02에서 검증했고 B-14에서 무료 개발 서버를 배포했다. 실제 보호소 사진 등록은 허가 후 진행한다. AI 초안 자동 생성은 별도이며 RN 재생 연결과 Q-01은 프론트의 캐릭터·화면 구조가 준비된 뒤 진행한다.

C-04 중 백엔드 기술은 Spring Boot·Supabase로 정해졌다. 맵 렌더러는 별도 결정이므로 C-04 전체를 완료로 처리하지 않는다. 배포 환경은 B-14에서 Render Free·Singapore로 정했다. 로그인 제공자와 화면 흐름, 사진 공개 조건은 별도 논의 항목이다.

B-12의 [사진 저장소 연결](photo-storage-connection.md)은 비공개 버킷·서버 키 연결과 실제 서명 URL 발급·PNG 다운로드·공개 접근 차단을 확인했다. 사진 기능을 켠 서버의 실제 DB 연결도 확인했다. 테스트 이미지는 앱 사진으로 등록하지 않았으며 실제 보호소 사진 등록·앱 로그인 화면 흐름은 남아 있다. B-14의 공개 개발 서버에서는 사진 기능을 꺼뒀다.

## 노션 상태를 바꾸는 시점

| 상태 | 시점 | 카드에 남길 것 |
| --- | --- | --- |
| 할 일 | 순서만 정했거나 선행 작업을 기다릴 때 | 완료 기준, 선행 작업 |
| 진행 중 | 해당 브랜치에서 실제 구현을 시작할 때 | 브랜치, 작업 범위, 착수 기록 |
| 확인 요청 | 구현과 관련 검증을 마치고 PR을 검토할 때 | PR URL, 검증 결과, 확인할 동작 |
| 완료 | GitHub 병합과 병합 코멘트 작성을 확인한 뒤 | PR URL, 병합 SHA, 결과와 남은 작업 |
| 보류 | 외부 정보·권한·결정을 기다려 더 진행할 수 없을 때 | 막힌 이유와 다시 시작할 조건 |

진행하지 않은 카드를 미리 옮기지 않는다. 실패한 테스트는 결과를 기록하고 `진행 중`에서 수정한다. 한 기능의 일부만 병합했다면 전체 카드의 완료 기준을 다시 확인한다.

이 상태 갱신은 작업자가 단계마다 수행한다. GitHub 이벤트와 노션의 자동 동기화는 현재 구현 범위에 포함하지 않는다.

## PR에 남길 내용

[PR 양식](../.github/PULL_REQUEST_TEMPLATE/backend.md)을 사용한다. 변경 파일 목록보다 사용자가 보게 될 동작과 변경 이유를 먼저 적는다.

- 무엇을 구현했는지, 이전과 어떻게 달라지는지
- 실행한 테스트·빌드와 실제 결과, 확인하지 못한 범위
- API 요청·응답 변경, DB 마이그레이션과 적용 여부
- 환경변수 이름과 실행 방법. 비밀 값은 제외
- 다음 작업에 넘길 내용과 연결할 노션 카드

병합 후에는 [병합 코멘트 양식](templates/backend-merge-comment.md)으로 PR의 대화 탭에 기록한다. 단순히 ‘완료’라고 적지 않고 구현 내용, 검증, SHA, 후속 작업을 남긴다.

B-13의 [실제 로그인·저장 검사](login-storage-verification.md)는 개발 프로젝트의 임시 일반 계정 2개로 사용자 등록·대화·메모 저장·타인 접근 차단·서버 재시작 보존을 확인했다. HTTP 기대 결과 65개를 통과했고 테스트 계정·앱 기록을 정리했다. 실제 사진 등록은 허가 전까지 보류하며 AI 호출 검증은 Q-02, 개발 서버 배포는 B-14에서 진행했다.

Q-02의 [실제 AI 검증](live-ai-verification.md)은 가상 질문 11개와 HTTP 기대 결과 124개를 통과했다. 1인칭 말투·관련 기록 설명을 보완했고, 실제 답변·근거 스냅샷·중복 호출 차단·오류와 명시적 재시도·서버 재시작 보존을 확인했다. API·DB 구조 변경은 없다. 개발 서버 배포는 B-14에서 진행했다. Q-01은 RN 준비 후, 실제 보호소 사진 등록은 허가 후 진행한다.
