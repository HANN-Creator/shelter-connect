# 백엔드 진행 규칙

Spring Boot와 Supabase PostgreSQL로 개발한다. 구현 기준은 Java 21, Gradle Wrapper다.

[노션 작업 보드](https://app.notion.com/p/3e15b2d1a55f819083b1de4e146a84d2)에서 작업을 하나씩 골라 진행하고, 카드와 PR을 서로 연결한다.

## 브랜치와 병합

`main` → `backend/<작업-ID>-<설명>` → PR → 검증 → squash merge

- 예: `backend/b-03-read-api`, `backend/b-06-chat-storage`
- PR 본문, 병합 코멘트, 노션에도 같은 브랜치 이름을 적는다.
- 새 작업은 최신 `origin/main`에서 시작한다. 한 카드에 한 PR을 대응시킨다.
- PR 제목에 작업 ID를 넣는다. 예: `[B-03] 보호소·강아지 조회 API 추가`
- 작업 중에는 Draft PR을 사용할 수 있다. 확인할 준비가 되면 Draft를 해제하고 노션을 `확인 요청`으로 바꾼다.
- 기능에 맞는 테스트와 필요한 빌드·CI를 통과하고 미해결 리뷰가 없어야 병합한다. 문서만 수정한 경우에는 문서 검토 결과를 적는다.
- 병합 직전에 검증한 HEAD SHA와 PR의 현재 HEAD SHA를 비교한다. 달라졌다면 변경 범위를 다시 검토한다.
- 병합 방법은 squash. PR 하나의 결과가 `main`에 커밋 하나로 남도록 한다.
- 브랜치는 병합 확인 뒤 정리한다. 기존 작업 브랜치나 사용자의 미완료 변경은 건드리지 않는다.

## 구현 순서

아래 순서로 한 작업씩 착수한다. ID는 기존 노션 카드와 맞추고, 진행 순서는 이 표를 따른다.

| 순서 | 카드 | 작업 | 끝났다고 볼 기준 |
| --- | --- | --- | --- |
| 준비 | C-05 | 브랜치·PR 진행 규칙 | 규칙과 양식 병합, 노션과 PR 기록 연결 |
| 1 | B-00 | 서버 기본 구성 | Spring Boot 실행, 환경변수 설정, 상태 확인, 테스트·빌드·CI |
| 2 | B-01 | 데이터 구조 정의 | 보호소·강아지·관찰·사진·사용자·대화 관계와 마이그레이션 정의 |
| 3 | B-02 | 샘플 데이터 | 가상 보호소 2곳·강아지 5마리, 관찰 기록, 반복 가능한 샘플 로딩 |
| 3-1 | B-02A | Supabase 개발 DB 초기 적용 | 지정 프로젝트에 V1과 샘플 적용, Flyway 호환·실제 건수 확인 |
| 4 | B-03 | 보호소·강아지 조회 API | 지역 필터·페이지 이동·빈 목록·비공개 제외, 초기 응답에 실제 사진 URL 없음 |
| 5 | B-04 | 인증과 보호소 권한 | 사용자 식별, 승인된 보호소의 소속 확인, 타 사용자·타 보호소 접근 차단 |
| 6 | B-05 | 동물 등록·수정 API | 기본 정보·관찰·입양 상태 변경과 요청 검증·권한 검사 |
| 7 | B-06 | 대화방·메시지 저장 | 강아지별 대화 유지, 소유권 검사, 같은 요청의 중복 저장 방지 |
| 8 | B-07 | 기록 기반 AI 연결 | 해당 강아지 기록만 사용, 미확인 질문과 실패·재시도 처리 |
| 9 | B-08 | 사진 조회 API | 사진 순서·빈 사진·공개 조건·비공개 저장소 주소 발급 |
| 10 | B-10 | 강아지 행동 설정 | 8개 동작용 속도·빈도·거리 설정 저장·조회, 보호소 확인과 수정 권한 |
| 10-1 | B-10A | Supabase 개발 DB V2·V3 적용 | 원격 이력·컬럼·제약·RLS·기존 데이터 보존 확인 |
| 11 | B-09 | 입양 준비 메모 | 본인 질문·돌봄 계획 저장과 재조회, 타 사용자 접근 차단 |
| 12 | B-11 | Spring Boot–Supabase 개발 DB 연결 | 실제 JDBC 연결·readiness·공개 API·미인증 차단 검증 |
| 13 | B-12 | Supabase 사진 저장소 연결 | 비공개 버킷·서버 키·실제 서명 URL 발급·이미지 다운로드 검증 |
| 연결 | Q-01 → Q-02 | 앱 연결·대화 품질 확인 | 실제 API의 보호소 → 대화 → 사진 흐름, 기록 준수와 응답 품질 확인 |

B-01은 기존 API 초안을 기준으로 [저장 구조](data-model.md)를 정의했다. 사용자 요청으로 B-03도 기존 초안을 따라 구현하고 [조회 응답 기준](read-api.md)을 문서화했다. B-04는 Supabase Auth 검증과 서버 DB 소속 검사로 구현했으며 [인증·권한 연결 기준](auth-and-permissions.md)을 따른다. C-02의 로그인 제공자·화면 흐름·사진 공개 조건과 C-03의 프론트 합의 전체가 끝난 것은 아니다. 실제 앱 연결 및 B-08 전에 남은 조건을 합의한다. B-05는 [동물·관찰 관리 API](dog-management-api.md)를 구현하고, 저장 트랜잭션의 권한 잠금과 동시 수정 검사를 적용했다. B-06은 사용자 요청에 따라 B-10보다 먼저 진행했고, [대화 저장 API](chat-storage-api.md)에 본인 소유권·중복 전송·상태 변경 검사를 구현했다. 사용자 요청으로 B-07도 이어서 구현했다. [기록 기반 답변](grounded-chat-api.md)은 V2 선점·재시도와 근거 확인을 사용하며, 실제 키 호출·답변 품질은 별도로 남아 있다. 개발 DB V2/V3는 이후 B-10A에서 적용했다. 사용자 요청에 따라 B-08도 B-10보다 먼저 구현했다. [사진 조회 기준](photo-read-api.md)은 본인의 완료된 답변 1회 후 공개와 사용 허가 검사를 적용한다. 횟수 1회는 기존 흐름을 바탕으로 둔 구현 기준이며 C-02 전체 합의는 별도이며 실제 Storage 설정은 이후 B-12에서 확인했다. 사용자 요청으로 B-10의 [8종 행동 설정](dog-behavior-api.md) 저장·확인·앱 조회도 구현했다. [B-10A 실제 DB 적용](supabase-development-db.md)도 완료했다. B-09의 [개인 입양 준비 메모](adoption-notes-api.md)도 구현했다. 기존 V1 테이블로 본인 메모의 저장·교체·단건·목록 조회와 동시 저장 충돌을 처리하며 DB 변경은 없다. B-11에서 [실제 서버↔개발 DB 연결](supabase-server-connection.md)과 HTTP 조회·미인증 차단을 검증했다. 실제 로그인 저장·AI 연결·보호소 사진 등록과 배포는 별도로 남아 있다. AI 초안 자동 생성은 별도이며 RN 재생 연결과 Q-01은 프론트의 캐릭터·화면 구조가 준비된 뒤 진행한다.

C-04 중 백엔드 기술은 Spring Boot·Supabase로 정해졌다. 맵 렌더러는 별도 결정이므로 C-04 전체를 완료로 처리하지 않는다. 로그인 제공자와 화면 흐름, 사진 공개 조건, 배포 환경도 별도 논의 항목이다.

B-12의 [사진 저장소 연결](photo-storage-connection.md)은 비공개 버킷·서버 키 연결과 실제 서명 URL 발급·PNG 다운로드·공개 접근 차단을 확인했다. 사진 기능을 켠 서버의 실제 DB 연결도 확인했다. 테스트 이미지는 앱 사진으로 등록하지 않았으며 실제 보호소 사진 등록·로그인 전체 흐름·배포는 남아 있다.

## 노션 상태를 바꾸는 시점

| 상태 | 시점 | 카드에 남길 것 |
| --- | --- | --- |
| 할 일 | 순서만 정했거나 선행 작업을 기다릴 때 | 완료 기준, 선행 작업 |
| 진행 중 | 해당 브랜치에서 실제 구현을 시작할 때 | 브랜치, 작업 범위, 착수 기록 |
| 확인 요청 | 구현과 관련 검증을 마치고 PR을 검토할 때 | PR URL, 검증 결과, 확인할 동작 |
| 완료 | GitHub 병합과 병합 코멘트 작성을 확인한 뒤 | PR URL, 병합 SHA, 결과와 남은 작업 |
| 보류 | 외부 정보·권한·결정을 기다려 더 진행할 수 없을 때 | 막힌 이유와 다시 시작할 조건 |

진행하지 않은 카드를 미리 옮기지 않는다. 실패한 테스트는 결과를 기록하고 `진행 중`에서 수정한다. 한 기능의 일부만 병합했다면 전체 카드의 완료 기준을 다시 확인한다.

이 상태 갱신은 작업자가 단계마다 수행한다. GitHub 이벤트와 노션의 자동 동기화는 현재 구현 범위에 포함하지 않는다.

## PR에 남길 내용

[PR 양식](../.github/PULL_REQUEST_TEMPLATE/backend.md)을 사용한다. 변경 파일 목록보다 사용자가 보게 될 동작과 변경 이유를 먼저 적는다.

- 무엇을 구현했는지, 이전과 어떻게 달라지는지
- 실행한 테스트·빌드와 실제 결과, 확인하지 못한 범위
- API 요청·응답 변경, DB 마이그레이션과 적용 여부
- 환경변수 이름과 실행 방법. 비밀 값은 제외
- 다음 작업에 넘길 내용과 연결할 노션 카드

병합 후에는 [병합 코멘트 양식](templates/backend-merge-comment.md)으로 PR의 대화 탭에 기록한다. 단순히 ‘완료’라고 적지 않고 구현 내용, 검증, SHA, 후속 작업을 남긴다.

Supabase 운영 DB에 적용하지 않았다면 로컬·CI에서 확인한 범위와 구분해서 적는다. PR 병합과 배포는 별개의 작업이다.
