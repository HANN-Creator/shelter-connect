# Q-02 실제 AI 호출과 답변 확인

가상 강아지 기록으로 실제 Luna 답변을 받고, Spring Boot를 거쳐 Supabase에 저장되는지 확인하는 작업이야. 프론트 화면이 없어도 여기까지는 먼저 확인할 수 있어. RN 화면에서 대화가 자연스럽게 이어지는지는 Q-01에서 따로 볼 거야.

## 다시 실행하려면

Java 21을 준비하고 `backend`에서 실행해. `.env.supabase`에는 지정 개발 DB 설정, `.env.storage`에는 임시 계정을 만들고 정리할 Supabase 서버 키가 필요해. `.env.ai.example`을 `.env.ai`로 복사하고 OpenAI 키를 넣어줘. 세 파일은 Git에서 제외돼. 값을 명령행에 직접 붙이거나 셸로 실행하지 않아.

```sh
python3 scripts/check_ai_live.py --project-ref <개발 프로젝트 ref> --check-config
python3 scripts/check_ai_live.py --project-ref <개발 프로젝트 ref>
```

첫 번째 명령은 설정 형식만 검사해. 두 번째 명령은 실제 외부 호출과 요금이 생길 수 있어. 일반 `build`, `test`, CI에서는 실행하지 않아.

검사는 다음 순서로 진행돼.

1. Auth·DB 프로젝트가 일치하고 강아지 이름·관찰 내용·상태가 저장소의 가상 샘플과 같은지 확인해. 낯선 관찰이나 변경된 기록이 있으면 전송 전에 멈춰.
2. 임시 일반 계정 두 개를 만들고 실제 비밀번호 로그인으로 서버에 접근해. 평소 쓰는 서버와 별도의 빈 로컬 포트를 사용해.
3. 짧은 인사에는 외부 모델을 부르지 않는지 확인해. 일부러 잘못된 키로 요청을 한 번 보내고, 실패 상태 저장·재시작 보존·자동 재시도 차단을 확인해.
4. 정상 키로 바꾼 후 명시적으로 재시도해. 이어서 [질문 10개](../backend/sample-data/ai/cases.json)를 순서대로 보내. 정상 완료 시 외부 요청은 실패 검사 1회와 답변 11회야. 실패하면 무한 재시도하지 않고 중단해.
5. 답변마다 같은 강아지의 확인된 관찰과 저장된 스냅샷을 대조해. 같은 요청이나 완료된 답변에 재시도를 보내도 다시 생성하지 않아야 해. 다른 계정은 접근할 수 없어야 하고, 서버를 다시 시작해도 같은 답변을 읽을 수 있어야 해.
6. 이번 실행에서 만든 계정 UUID와 실행 표식을 확인한 뒤 그 계정의 메시지·근거·대화방을 정리해. 기존 12개 앱 테이블의 행 수가 같아야 해.

## 답변을 읽는 기준

질문은 친해지는 방법, 산책, 공놀이, 철회된 관찰, 모르는 생일, 미확인 접종, 안전·입양 보장, 다른 강아지와의 혼동, 지시문 무시, 이전 사용자 발언으로 나눴어. 정상 키로 재시도하는 질문까지 총 11개야.

자동 검사는 처리 상태와 근거 ID·저장 결과를 확인해. 그 뒤 답변을 직접 읽고 다음을 확인해야 해.

- 관찰한 한 번의 행동을 항상 그렇다고 확대하지 않는지
- 다른 강아지나 사용자 발언을 자신의 사실로 말하지 않는지
- 건강·안전·입양을 보장하거나 없는 날짜를 만들지 않는지
- 한국어 1인칭 반말이 자연스럽고 1~3문장으로 짧게 답하는지

`build/login-check-*/ai-report.json`에 질문·실제 표시 답변·근거·지연 시간·사용량을 남겨. 이 보고서의 `manualReviewRequired`는 자동 검사 통과를 사람의 내용 검토로 오해하지 않도록 항상 true야. 검토 결과는 이 문서에 따로 기록해. `cleanup-complete.txt`까지 있어야 테스트 계정과 기록 정리를 마친 거야. 정리 실패 시 해당 실행의 `created-users.txt`를 기준으로 확인하고, 이메일 패턴으로 일괄 삭제하면 안 돼.

## 사용량과 서버 실행

서버 로그에는 HTTP 상태, 호출 시간, 모델 이름, 입력·캐시 입력·출력·추론 토큰 수만 남겨. API 키·질문·답변·사용자 식별자는 기록하지 않아. 사용량이 빠지거나 잘못된 숫자면 0으로 계산하지 않고 `unavailable`로 표시해. 추론 토큰은 출력 토큰의 일부라 비용에 두 번 더하지 않아.

모델은 [gpt-5.6-luna](https://developers.openai.com/api/docs/models/gpt-5.6-luna), Responses API, `reasoning.effort=low`, 출력 상한 2,000토큰이야. [공식 가격표](https://developers.openai.com/api/docs/pricing)는 실행 날짜 기준으로 확인해. 토큰 계산은 예상 비용이고, 실패·응답 유실·캐시 쓰기 비용을 포함한 최종 청구서는 별도로 확인해야 해.

평소 개발 서버에서 AI를 켜려면 다음처럼 명시적으로 실행해.

```sh
python3 scripts/run_supabase.py --with-ai --check-config
python3 scripts/run_supabase.py --with-ai
```

`--with-ai`가 없으면 로컬 파일이나 상위 환경에 키가 있어도 AI는 꺼져 있어. 사진 기능이 필요하면 기존 `--with-photos`를 같이 사용할 수 있어. 실제 보호소 사진 등록은 허가 전까지 보류해.

## 확인 범위

API·DB 구조 변경이나 마이그레이션은 없어. 원격 RLS, 보호소 담당자 권한, 실제 사진 등록과 외부 서버 배포도 이번 범위에 포함하지 않아. 대량 동시 접속·장기 지연 분포·모든 질문의 사실성은 이 작은 샘플만으로 보장할 수 없어. 429·시간 초과·동시 생성 제어는 모의 HTTP와 PostgreSQL 통합 테스트에서 확인하고 실제 서비스에 고의 부하를 주지 않아.

## 검증 중 고친 내용

첫 실행에서는 콩이가 자신을 3인칭으로 말했고, 밤이는 관련 놀이 기록이 있는데도 확인 안내만 반환했어. 두 번째 실행에서는 이 두 문제가 해결됐지만, 두부에게 콩이를 언급하며 공놀이를 물었을 때 자기 기록까지 설명하지 않는 응답이 나왔어. 두 실행 모두 저장·근거 스냅샷·중복 요청·타인 접근 차단·서버 재시작·명시적 재시도 검사는 통과했고, 품질 기준 미달을 성공으로 처리하지 않았어.

지시문은 1인칭 말투, 한 번 관찰한 행동의 범위, 하지 않은 행동도 유효한 관찰이라는 점을 명확히 했어. 다른 강아지 이름이 질문에 등장하더라도 해당 강아지의 확인된 기록으로 답할 수 있는 부분을 설명하게 했어. 미확인 건강·안전·입양 판단을 보호소에 확인하는 규칙과 서버의 근거 검사는 유지했어.

근거 번호는 `sample-data/dataset.json` 관찰 ID의 마지막 세 자리야. 다른 강아지·초안·철회 기록은 근거에 포함되지 않았어. 단순 인사는 모델 호출 없이 처리했고, 이미 끝난 답변은 재전송·명시적 재시도·서버 재시작 후에도 재생성하지 않았어.

마지막 11회 성공 호출의 관측값은 다음과 같아. 배포된 앱이나 다수 사용자 환경의 성능을 뜻하지는 않아.

| 항목 | 값 |
| --- | --- |
| OpenAI 응답 대기 | 평균 2.35초, 중앙값 2.37초, 1.64~3.21초 |
| 로그인된 로컬 `/reply` 요청 전체 | 평균 8.84초, 중앙값 9.14초, 7.27~10.06초 |
| 입력 / 캐시 입력 토큰 | 12,761 / 0 |
| 출력 / 그중 추론 토큰 | 1,337 / 342 |
| 일반 입력·출력 단가 기준 참고 금액 | 약 $0.0042 |

세 차례 검증 전체에서는 성공 응답 33회와 잘못된 키 오류 검사 3회가 있었어. 성공 응답 사용량 합계는 입력 34,233토큰, 출력 4,258토큰이며 추론 1,313토큰은 출력에 포함돼. 일반 입력·출력 단가로만 계산하면 약 $0.0120이야.

금액은 2026.09.21 공식 Standard 짧은 문맥 단가(100만 토큰당 일반 입력 $0.20, 출력 $1.20)를 관측한 성공 응답에 적용한 참고 계산이야. 캐시 쓰기 단가 $0.25 적용 여부를 이 로그에서 구분할 수 없고 실패 요청의 청구도 여기서 확정하지 않아. 대시보드의 최종 청구 금액과 같다고 보장하지 않아.

API 전체 시간에는 생성 전후의 원격 DB 처리도 들어가. 모델 시간보다 길게 측정됐으므로 배포 후 서버·DB 구간별 시간을 다시 측정하고, RN에서는 답변을 기다리는 상태를 표시해야 해. 이번 작은 회귀 검증을 모든 질문의 정확성이나 장기 응답 속도 보장으로 보지는 않아. 같은 모델도 이후 응답은 달라질 수 있어.

최종 실제 검사에서는 HTTP 기대 결과 124개를 통과했고, 마지막 실행의 임시 계정 2개와 대화방 4개·메시지 24개·근거 스냅샷 7개를 정리했어. 앞선 두 실행도 정리를 마쳤고 각각 기존 12개 앱 테이블의 행 수가 복원된 것을 확인했어. 검사 서버도 모두 종료했어.

공유 검증 도구를 바꿨기 때문에 기존 B-13도 실제로 다시 실행해서 65개 HTTP 기대 결과와 정리를 확인했어. Python 검사 14개, Java 검사 272개와 빌드를 통과했어. PostgreSQL 통합 검사와 패키징 검사는 PR CI에서 확인해.
