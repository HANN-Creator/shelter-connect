# B-51 기준 도트 눈 표현 검사

최근 세 강아지의 32px 기준 도트에서 눈이 검은 털에 묻히거나 속이 빈 테두리처럼 보였다. 기존 생성 지시의 “작고 자연스러운 눈”만으로 눈 표현이 유지되지 않았고, 행동 검수는 이미 승인된 기준 도트를 정답으로 사용했다.

## 새 작업의 처리

1. 사진과 기존 승인 스타일을 그대로 사용한다. 공통 `seedEyes` 규칙은 털과 구분되는 작은 채워진 동공, 절제된 반사점, 방향별 위치·크기 일관성을 지정한다. 빈 고리·큰 흰자·화난 실눈은 거절한다.
2. PixelLab이 4방향 기준 도트를 만들면 서버의 `StyledSeedQualityAgent`가 사진·승인 스타일·네 방향 원본을 함께 Luna에 전달한다. 기준 도트는 아직 승인되지 않은 검사 대상임을 명시한다.
3. 정면·좌우의 읽기 쉬운 눈과 스타일, 뒷면의 얼굴 비노출, 사진 외형을 검사한다. 불확실한 응답도 통과시키지 않는다. 방향별 중복/누락과 잘못된 응답은 검사 오류로 중단한다. 가장자리 접촉은 원본 픽셀로 별도 확인한다.
4. 시각 불합격은 기준 도트만 최대2회 다시 생성한다. 각 시도는 기존 `repair_count`/`attempt_history`에 저장하고 사진·그림체·9프레임 규약은 유지한다. 실패한 기준 도트 파일은 덮어쓰지 않는다. 명확한 검사 오류·접수 불명은 자동 재전송하지 않는다.
5. 통과한 기준 도트도 기존 담당자 승인 후에만 행동을 생성한다. 2회 보완 후 불합격이면 `SEED_REVIEW`에 머물고 `SEED_QUALITY_REVIEW_REQUIRED`를 반환한다. 승인 API와 행동 작업 선점 양쪽에서 이 조건을 검사한다.

검사 결과는 `steps[0].qualityReport`로 제공하며 네 방향 파일 해시·규칙 해시와 결합된다. 다른 이미지의 통과 기록으로 승인할 수 없다. 새 작업의 `qualityPolicy.seedQualityVersion`은 `seed-eyes-v1`이다. 기존 승인된 작업은 소급 변경하지 않는다. API 요청 형태·DB 구조는 바뀌지 않는다.

공통 품질 규칙은 `sprite-regressions-2026-10-06-v7`로 갱신한다. 다른 규칙 해시로 진행 중이던 작업은 기존 정책대로 `QUALITY_RULES_CHANGED`에서 멈춘다. 재검토·새 생성은 별도 명시 절차이며 기존 보완 예산을 초기화하지 않는다.

## 검증 자료와 경계

- `seed-eye-regressions.json`: 최근 실제 실패 도트의 해시와 사람이 확인한 결함 종류. 원본 사진·도트 바이트는 승인된 비공개 로컬 검증 폴더에만 보관한다. 해시 목록 자체를 시각 검출기로 표현하지 않는다.
- 단위 검사(관련 26개 통과; 실제 API 전송 검사는 기본 생략): 정면/좌우의 실패·불확실 응답 차단, 뒷면 얼굴 차단, 외형 실패, 중복 방향, 규칙·이미지 해시 결합, 최대 길이 입력과 보완 요청의 전달.
- PostgreSQL 검사(관련 38개 통과; 기존 실제 API 전송 검사는 기본 생략): 불합격 기준 도트 자동 보완, 과거 결과·영수증 보존, 최대2회 제한, 담당자 승인 우회 차단, 행동 유료 호출 차단, 검사 오류의 무한 재시도 방지, 기존 생성·저장·학습 흐름의 회귀 검사.
- Python 공통 생성·회귀 검사 31개 통과. Java 빌드와 JAR 생성 통과.
- 실제 생성: 승인된 오슈 사진으로 같은 백엔드 payload builder와 PixelLab을 사용해 4방향 기준 도트를 다시 생성했다. 사람 검수에서는 정면과 양옆 눈의 명암 구분이 개선되었다. 원본 32px 픽셀에 사후 눈 그리기나 블러를 적용하지 않았다.
- 실제 Luna 새 기준 도트 검사와 개발 서버 배포는 아직 검증하지 않았다. 모의 모델 응답 테스트를 실제 시각 정확도 통과로 보고하지 않는다.

CLI는 같은 생성 예방 규칙을 사용하지만 명시적인 사람의 기준 도트 검토가 필요하다. 자동 Luna 검사와 제한된 보완은 서버 워커 경로다.
