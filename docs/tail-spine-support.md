## 재현한 문제

배포 작업 `2896c6d7-4809-4275-9e09-43ec4c8ace9c`는 BASE WEST의
`rearBranchSupport=false` 때문에 `SEED_OBSERVATION_UNCERTAIN`으로 정지했다.
원본은 네 방향 모두 그대로 보존했고, 실제 AI 관찰 두 번은 양쪽 꼬리를
`COMPLETE_CONNECTED / CONNECTED / DISTINCT / VISIBLE`로 기록했다.
여백과 연결 성분 검사에도 문제가 없었다. 제출은 1회, 보완은 0회이며 공개되지 않았다.

얇게 만든 실루엣 경로가 꼬리 끝 `(24,14)`에서 몸통을 지나 머리 `(10,9)`까지
이어졌다. 기존 코드는 경로의 마지막 점만 검사하여 중간의 몸통 연결점을 놓쳤다.
좌우를 뒤집어도 판정이 같아야 한다는 새 검사 역시 수정 전에는 실패했다.

## 변경

`rear-silhouette-branches-v2`는 최소 네 점, 뒤쪽 끝점, 중앙 1/3 영역과
2px 이상의 높이 차이라는 기존 조건을 경로 중간에서도 검사한다.
처음 발견한 연결점까지의 경로만 근거로 저장한다. 기존 뒤쪽 분기점 판정은 유지한다.
이 사례에서는 `(20,19)`에서 연결 근거를 확인한다.

측정 복사본만 사용하며 원본 PNG에는 변형을 가하지 않는다. 실루엣 근거만으로
꼬리라고 단정하지 않고, 별도의 AI 해부학 관찰·연결 성분·가장자리 검사를 모두 유지한다.
실제로 없는 꼬리, 떨어진 조각, 잘림과 내려가는 다리 경로를 통과시키는 예외가 아니다.
기존 승인 결과를 바꾸거나 보완 예산을 초기화하지 않는다.

최초 생성·보완 결과·명시적 재검수가 같은 서버 측정기를 사용한다.
공통 규칙 파일과 CLI 하네스에도 원본 해시와 회귀 사례를 남겼다.
과거 검수 결과의 판정을 로컬에서 재현하는 것은 회귀 검사이며,
그 결과를 새 서버 승인 영수증으로 사용하지 않는다.

## 실제 AI 검수 결과와 미완료 범위

고친 측정기를 사용해 같은 사진·같은 네 PNG를 실제 Luna로 재검수했다.

| 검사 | 실제 결과 |
| --- | --- |
| 꼬리 전용 검수 | PASS, 사진 관찰 1회 + 양쪽 도트 관찰 1회 |
| 전체 BASE 검수 중 꼬리 | PASS, 양쪽 도트 관찰 1회 |
| 전체 BASE 품질 | **FAIL**: SOUTH 털무늬 관찰 충돌, WEST/EAST BODY_PATTERN_MISSING |
| 추가 PixelLab 생성 | 0회 |
| 원본 PNG 변경 | 없음 |
| 원격 작업 상태·승인 변경 | 없음 |

전체 검수는 통과하지 않았다. `StyledTailSpineLiveTest`의 전체 통과 assertion도
실제로 실패했고, 그 실패를 재호출로 덮지 않았다. 이전 배포 검수의 털무늬 통과와
새 전체 검수의 판단 차이를 모두 보존한다. 이 새 판단을 곧바로 학습 정답으로
사용하거나 자동 공개 근거로 바꾸지 않는다.

추가로 현재 `StyledSeedRepair.plan`은 어느 방향이든 털무늬 관찰이 불확실하면
전체 선택 보완을 중단한다. 따라서 다른 방향에 확정 결함이 있어도 보완이 막힐 수 있다.
이것은 꼬리 경로 수정과 별개의 검수·보완 정책 문제다. 사용자는 명확한 결함만
차단하고 애매한 명암·그림체·무늬 표현은 경고로 기록하는 정책을 선택했다.
[B-77](https://app.notion.com/p/3f45b2d1a55f8003be7afb5db0080409)에서 별도 PR로 구현하며,
두 변경을 함께 검증한 뒤 배포한다. 이 PR만으로 새 정책을 적용했다고 보고하지 않는다.

실제 원본·이전 판정·새 꼬리/전체 판정은
`backend/scripts/fixtures/tail-spine-v31/evidence.json`과 해시로 묶여 있다.
실제 사진은 허가된 로컬 검증 자료에만 있으며 저장소에 넣지 않았다.

## 검증 및 배포 경계

신규 회귀 검사는 수정 전 정상 꼬리·좌우 대칭 두 항목이 실패했고 수정 후 통과했다.
기존 정상·누락·잘림·분리·사진에서 안 보이는 꼬리·불확실 관찰·유료 보완 차단
검사도 함께 실행한다. 실제 전체 품질 실패와 오프라인 코드 검사의 결과는 별도로 기록한다.

이 단계에서는 병합·배포·원격 자동 승인·12모션·앱 재생을 완료로 보고하지 않는다.
남은 검수 충돌을 해결한 뒤 같은 원격 작업을 정상 재검수 API로 이어가야 한다.
다른 강아지로 바꾸거나 DB의 판정·상태·횟수를 직접 수정하여 실패를 우회하지 않는다.
