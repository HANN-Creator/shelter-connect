# 실제 로그인과 개인 기록 저장 확인

B-13은 실제 Supabase Auth에서 발급한 사용자 토큰을 Spring Boot에 보내고, 개발 DB에 대화와 입양 준비 메모가 저장되는지 확인하는 작업이야. 프론트 화면 없이도 서버까지의 연결은 먼저 검증할 수 있어.

## 확인하는 흐름

1. 지정 개발 프로젝트에 임시 일반 사용자 두 명을 만들고 이메일·비밀번호로 로그인해. 메일을 보내지 않는 테스트 전용 주소를 사용하고, 기존 계정이나 보호소 담당자 권한은 바꾸지 않아.
2. 등록 전 접근은 403, `POST /v1/me` 등록과 반복 호출은 같은 사용자로 처리되는지 확인해. 보호소 소속은 빈 목록이고 관리 경로는 403이어야 해.
3. 봄이·두부의 대화방을 만들고 메시지를 저장해. 같은 요청을 다시 보내면 같은 메시지, 같은 요청 ID에 다른 내용이면 409여야 해. 다른 계정은 대화방·메시지 조회와 저장을 할 수 없어.
4. 입양 준비 메모를 만들고 조회·수정해. 오래된 버전과 중복 생성은 409, 같은 내용의 재저장은 기존 시각을 유지해야 해. 같은 강아지라도 두 계정의 메모는 따로 저장돼야 해.
5. 이 도구가 실행한 서버를 종료하고 다시 실행해. 두 계정 모두 다시 로그인한 뒤 사용자·대화·메모 ID와 내용·수정 시각이 그대로인지 확인해.
6. 이번 실행에서 만든 Auth 사용자와 본인 앱 기록만 정리해. 원래 12개 앱 테이블의 행 수가 모두 복원됐는지도 확인해.

목록의 커서를 다른 계정에 넘겼을 때의 차단, 비공개 강아지 대화 생성 차단, 잘못된 토큰·서버 키의 사용자 토큰 대체 차단도 함께 확인해. API 응답은 `no-store`와 요청 식별자를 검사해.

## 실행 방법

Java 21, 기존 `.env.supabase`의 개발 DB 접속 설정, `.env.storage`의 서버 키가 필요해. 이 파일들은 Git에서 제외돼 있어. 프로젝트 ref는 대시보드 주소의 `project/` 뒤 값이고, 입력한 ref와 로컬 설정이 다르면 접속 전에 중단해.

`backend` 폴더에서 실행해.

```sh
python3 scripts/check_login_storage.py --project-ref <개발-프로젝트-ref>
```

도구가 서버 JAR을 빌드하고 비어 있는 로컬 포트에서 실행해. 평소 쓰는 8080 서버나 다른 프로세스를 종료하지 않아. AI·사진 기능과 DB 자동 변경은 꺼져 있고, 서버 키는 테스트 계정 관리에만 쓰며 Spring Boot 프로세스에는 전달하지 않아.

일반 `build`, `test`와 CI에서는 실제 Supabase 검사를 실행하지 않아. 실제 계정 생성·저장이 있으므로 지정 개발 프로젝트에서만 위 명령을 직접 실행해. CI는 설정 가드 검사와 기존 PostgreSQL 통합 검사만 실행해.

## 테스트 데이터 정리

사용자 UUID와 실행별 표식이 일치하는 이번 실행의 계정만 대상으로 해. 앱 기록은 `auth_provider`·`auth_subject`로 해당 사용자를 찾고 트랜잭션으로 정리해. 역할이 USER가 아니거나 보호소 소속이 생겼다면 정리를 멈춰. 예상 밖 참조는 DB 제약으로 차단하고, 넓은 이메일 패턴이나 전체 삭제는 사용하지 않아.

검사 중 오류가 나도 서버 종료와 정리를 시도해. 프로세스 강제 종료·네트워크 장애로 정리가 끝나지 않으면 `backend/build/login-check-*/created-users.txt`의 정확한 테스트 UUID와 실행 표식을 확인해야 해. Auth 계정 생성 응답이 유실돼 생성 여부를 모르는 경우에도 정리 완료로 표시하지 않아. 비밀번호와 토큰은 파일·출력에 남기지 않아. 기록 폴더는 본인만 열 수 있고 Git·서버 JAR에도 포함되지 않아. `cleanup-complete.txt`는 정리와 원래 행 수 확인까지 끝난 경우에만 생성돼.

## 이번 결과

2026.09.21 지정된 `shelter-connect-dev`에서 실제 검사를 마쳤어. 위 흐름의 HTTP 기대 결과 65개를 모두 통과했어. 실제 ES256 사용자 토큰으로 등록·저장했고, 서버를 종료한 뒤 새 프로세스와 새 로그인으로 동일한 기록을 확인했어.

테스트 Auth 계정 2개와 앱 사용자 2개, 대화방 3개, 메시지 2개, 메모 3개를 생성·검증한 뒤 모두 정리했어. 삭제한 Auth 계정은 다시 조회했을 때 404였고, 기존 12개 앱 테이블의 행 수는 검사 전과 같았어. 가상 보호소·강아지·관찰 기록, 기존 사용자, DB 구조·RLS·담당자 권한은 바꾸지 않았어. 확인용 서버도 종료했어.

로그인·저장 서버 코드를 고칠 문제는 발견되지 않았어. 다시 확인할 수 있는 수동 검증 도구와 프로젝트 대상 가드 검사만 추가했어. Python 검사 11개와 Java 검사 268개·빌드도 통과했어. PostgreSQL 통합 검사는 PR CI에서 확인해.

## 다음에 확인할 부분

이 검사는 이메일·비밀번호 로그인으로 서버의 인증·저장 연결을 확인하는 거야. 회원가입 메일 확인, 카카오·구글 로그인, 앱에서 토큰 갱신·로그아웃하는 화면 흐름은 별도로 연결해야 해. 보호소 담당자 초대·권한 부여, 실제 AI 답변 호출·품질 확인과 배포도 별도야.

실제 보호소 강아지 사진 등록은 사용 허가를 받을 때까지 보류해. 이번 검사에는 가상 강아지와 직접 작성한 테스트 문장만 사용해.

계정 준비와 로그인 방식은 Supabase의 [서버에서 사용자 생성](https://supabase.com/docs/reference/javascript/auth-admin-createuser), [이메일·비밀번호 로그인](https://supabase.com/docs/reference/javascript/auth-signinwithpassword), [서버 키 사용](https://supabase.com/docs/guides/api/api-keys)을 기준으로 했어.

이후 실제 AI 호출·가상 질문 답변 검토는 [Q-02](live-ai-verification.md)에서 확인했어. 이 문서의 로그인 검사는 계속 AI를 끈 상태로 실행해.
